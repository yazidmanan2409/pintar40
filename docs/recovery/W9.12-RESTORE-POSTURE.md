# W9.12: recovery readiness after a logical restore

**Status: implemented, not yet proven.** The proof is a dispatch of `.github/workflows/restore-rehearsal.yml` from
`main`. That needs this change merged to `main` first, because the job only runs from `refs/heads/main`. Until a run
of that workflow is green, nothing here says the restored copy is launch-ready.

## What run 41594063773 (3 Nov) found

The documented logical restore of staging into an empty local stack kept every PINTAR table's data. After the first
corrected step (PINTAR's `auth.users` triggers), `docs/audit/launch-readiness.sql` was 18 PASS, 6 FAIL
(`docs/completion-4.0/batch-4/03-RECOVERY-GATE.md`):

| # | Failing row (launch-readiness.sql) | Measured on the copy |
|---|---|---|
| 1 | anonymous surface unchanged (line 216) | 10 / 19 / 509 anon functions |
| 2 | audit trail is append-only (line 169) | 9 client write grants |
| 3 | G7 anon holds no right (line 243) | 142 relations |
| 4 | G7 authenticated executes exactly the registered functions (line 263) | 289 of 509 differ |
| 5 | G7 authenticated holds exactly the release's table rights (line 257) | 228 differ |
| 6 | G7 the assets bucket exists and is private (line 300) | missing |

## The cause

**Rows 1 to 5: privileges.** PINTAR is closed by default. Migration `20260912004158_foundation_base.sql:14-22` revokes
everything Supabase grants `anon` and `authenticated` on `public`, and changes postgres's default privileges so later
objects start closed. `20260912004654_function_privileges.sql:15-29` revokes EXECUTE from PUBLIC on every function.
`20260912051935_audit_log_no_service_writes.sql:8` takes UPDATE, DELETE and TRUNCATE on `audit_log` from
`service_role`. Each later migration then grants rights back one at a time.

`pg_dump`, which `supabase db dump` runs (workflow lines 121-123), writes each object's rights relative to Postgres's
built-in default. The built-in default names only the owner (and PUBLIC, for functions). So the dump has GRANTs, but
no REVOKE for `anon`, `authenticated` or `service_role`. Its own `ALTER DEFAULT PRIVILEGES` is restored after the
objects.

The empty stack's default privileges give those three roles ALL on every table, sequence and function postgres
creates in `public`. So every restored object starts fully open, staging's GRANTs are added on top, and nothing
takes the rest away:

- anon may execute all 509 functions (row 1);
- anon may touch every relation (row 3);
- authenticated may do anything (rows 4 and 5);
- all three roles may write `audit_log`: 3 roles × UPDATE/DELETE/TRUNCATE = 9 grants (row 2).

The dump's `ALTER DEFAULT PRIVILEGES` comes out relative to the built-in default too, so the copy's defaults stay open
as well. Every table a later migration created on the copy would also start open.

A local reproduction (PostgreSQL 16 `pg_dump`, roles and defaults set up like Supabase's) showed exactly this. The dump
held only GRANT lines. On the copy, anon held all rights on every table, sequence and function, and the default
privileges stayed open.

**Row 6: the bucket.** `20260912004550_storage_config.sql:7-9` inserts the private `assets` bucket as a row of
`storage.buckets`. The data dump does include that row. But the runner's stack runs an older Storage version than
staging (03-RECOVERY-GATE.md, item 3). Staging's `storage.buckets` has columns the copy's table lacks, so that row's
`COPY` fails and the table stays empty. The 3 Nov run listed the bucket row as "differs".

The local reproduction (staging's table given one extra column) failed with
`column "type" of relation "buckets" does not exist`. The real column set on the runner is only seen on dispatch.

## The corrected step

It runs after the trigger step: "The second corrected step - PINTAR's privileges and the private bucket, re-applied
from staging's own catalog, then the launch-readiness checks again". It calls `scripts/recovery/restore-posture.sh`.

1. **Read staging, read only.** `scripts/recovery/posture-acl.sql` lists every right that PUBLIC, `anon`,
   `authenticated` and `service_role` hold. It covers the schemas, tables, views, sequences, columns and routines of
   `public`, `telemetry` and `pintar_permintaan`, plus postgres's default privileges (global and per schema).
   A NULL ACL is read as its built-in default.
2. **Re-apply on the copy.** `scripts/recovery/posture-apply.sql` runs as one transaction. It revokes all rights from
   those four grantees on every such object of the copy, and on the default privileges. It then grants exactly what
   staging holds and counts any staging right whose object the copy lacks.
3. **Compare.** It reads the copy's rights again and diffs them against staging's.
4. **Buckets.** It takes the columns both `storage.buckets` tables have, copies staging's rows over them, and upserts
   them on `id`. Then it compares the two row sets by hash.
5. **Readiness again.** The workflow reruns `fakta.sql`/`banding.sh` and `launch-readiness.sql`.

The step fails the job if any of these holds:

- any readiness row is FAIL or ERROR;
- the rights differ in either direction;
- the bucket rows differ.

Only counts, kinds, object names and bucket ids are printed. The work directory is removed by "Discard the backup".

## What a green dispatch from main proves

Staging's logical backup, restored into an empty Supabase stack, gets all of these back:

- every table;
- PINTAR's `auth.users` triggers;
- PINTAR's exact client-role rights and default privileges;
- its private bucket.

Recovery is then the documented restore plus these two corrected steps, and the result passes every launch-readiness
check, the G7 rows included.

It does not prove any of the following:

- Storage files (metadata only);
- secrets outside the database;
- Auth/SMTP settings;
- a restore into a hosted project.

## Verified locally vs. only on dispatch

- **Locally:** the workflow YAML parses, and every `run:` block and the script pass `bash -n`. The scripts were run
  against a throwaway PostgreSQL 16 pair (a "staging" and a pg_dump-restored "copy" with Supabase-like defaults). The
  rights went from 73 beyond staging's to 0 both ways. The bucket was re-created as private. A second run was clean.
  A planted staging-only function was reported, and the script exited 1.
- **Only on dispatch:** Postgres 17 and the real Supabase roles. Whether postgres on the local stack can revoke every
  grant, since grants made by another grantor are not revocable by postgres; the diff would report them. The real
  bucket column sets. The actual readiness result.
