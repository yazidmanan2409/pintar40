# 03 — PINTAR Invariants

The authoritative rule list. Every one of these must remain true regardless
of which UI, API shape, or database engine implements it. Treat additions
to this list as requiring the same rigor as adding a new invariant test.

| ID | Rule | Why it exists | Where enforced | How tested |
|---|---|---|---|---|
| INV-01 | Answer keys (option correctness, rationale-to-correct mapping) never reach an unauthenticated or learner-scoped client payload. | The entire assessment's validity depends on this; a leak invalidates every certificate issued against the leaked content. | DB (RLS/view grants) + server (response sanitization before serialization) | Black-box REST test: fetch an item as a real learner JWT, assert no `is_correct`/rationale field present. |
| INV-02 | A hint/scaffold field can never name or narrow to the correct option. | Core Learning Safety Doctrine — assistance must never reveal the answer. | DB (CHECK constraint, regex) + server (dynamic hint generation validated against the same rule) | Attempt INSERT/UPDATE of a hint containing the answer text; assert rejection. Fuzz-generate hints and re-run the same check. |
| INV-03 | Every Option's rationale is non-empty. | A wrong answer is evidence of thinking; an unexplained distractor teaches nothing. | DB (`NOT NULL` + non-empty CHECK) | Attempt INSERT of an Option with empty rationale; assert rejection. |
| INV-04 | Once a PLP Release is FROZEN, its taught-content columns (lessons, items, options, blueprints covered by the hash) cannot be modified. | Certificates and audit trails must point at content that provably didn't change after assessment. | DB (immutability trigger) | Attempt UPDATE on a frozen release's item; assert rejection. Recompute hash after an allowed metadata-only update; assert unchanged. |
| INV-05 | A Certificate always carries the exact `plp_release_id` (or equivalent) of the content the learner was assessed against, outside the signature payload but permanently bound. | Enables reconstructing exactly what was taught, indefinitely, without coupling to identity-model churn. | DB (FK, not null once PLP-based) + server (issuance path) | Issue a certificate; assert `release_id` is present and queryable independent of the HMAC payload. |
| INV-06 | Certificate verification uses a timing-safe comparison. | Prevents timing side-channel forgery of valid certificates. | Server (verification function) | Static/code-level test asserting the comparison function used; behavioral test asserting near-miss hashes fail identically fast. |
| INV-07 | Certificate signing keys are versioned; rotating the active key never invalidates a certificate issued under a prior version. | Security incidents must be recoverable without destroying historical credentials. | DB (`key_version` column) + server (keyring lookup) | Issue under V1, rotate to V2, re-verify the V1 certificate; assert success. |
| INV-08 | `learner_id`/`user_id` on any session, response, or certificate is derived server-side from the authenticated session — never trusted from a request body. | Prevents identity spoofing / attribution forgery. | Server (every write path) | Attempt to submit a response/finalize a session with a forged `user_id` in the body; assert the server ignores it and uses its own derived id. |
| INV-09 | Final score and safety-gate pass/fail are computed server-side from raw responses — never trusted from a client-submitted summary — and recomputed independently a second time at certificate issuance. | Two deliberately redundant gates against a single point of forgery. | Server (finalize + issuance paths) | Submit a forged high score in a finalize request; assert the server-computed score is used. Tamper with the stored summary between finalize and issuance; assert issuance recomputes and catches the mismatch. |
| INV-10 | A safety-critical item answered wrong fails the attempt regardless of overall score. | The Safety Gate must never be defeated by aggregate performance. | DB (blueprint rule) + server (gate evaluation) | Construct a session passing overall score but failing one safety-critical item; assert overall result is FAIL. |
| INV-11 | Hesitation/assistance telemetry never influences scoring. | Assistance exists for learning, not for penalizing help-seeking. | DB (physically separate columns/table, no FK from any scoring view) | Query every scoring-relevant view/function; assert none references the assistance telemetry table/columns. |
| INV-12 | An `EXAM`-tier item can never be drawn into a `PRACTICE`- or `TEST`-configured assessment session. | High-stakes item security; prevents item leakage through lower-stakes exposure. | DB (constraint on session-assembly query / bank_type check) | Attempt to assemble a PRACTICE session that includes an EXAM item; assert refusal. |
| INV-13 | Tenant A's data (content, sessions, certificates, briefings) is never readable by Tenant B, regardless of role, except where explicit cross-institution sharing is a stated V1 feature. | Multi-tenant trust boundary. | DB (RLS keyed off ancestor-path/`institution_id`) | Two seeded institutions; authenticate as a role in Institution A; assert zero rows visible from Institution B on every tenant-scoped table. |
| INV-14 | Every `SECURITY DEFINER` function pins its `search_path` explicitly. | Prevents search-path hijacking privilege escalation. | DB (function definition) | Schema-lint query against `pg_proc`/`pg_settings`; assert no `SECURITY DEFINER` function has an unpinned `search_path`. |
| INV-15 | No storage bucket serving licensed/private content grants `SELECT`/`INSERT`/`UPDATE` to `public` or `anon`. | The C2 root cause, generalized. | DB (storage policies) | Anonymous fetch of a known object path; assert refusal. Anonymous/authenticated attempt to overwrite an existing object; assert refusal unless via the server-gated route. |
| INV-16 | A user can never self-grant a role above STUDENT; only an active SYSTEM_ADMIN may grant SYSTEM_ADMIN or platform-level roles. | Anti-privilege-escalation. | DB (grant trigger) | Attempt self-grant as a non-admin; assert rejection. Attempt a non-SYSTEM_ADMIN granting SYSTEM_ADMIN; assert rejection. |
| INV-17 | A role/scope revocation takes effect on the next server-side check, including mid-session — an expired grant must interrupt an in-progress session, not just block the next page load. | Time-bounded access must actually bound access. | Server (middleware + session-check on every scored action) | Revoke a grant mid-session; attempt the next scored action under the old session; assert refusal. |
| INV-18 | Every role-grant, item edit, release freeze, and certificate issuance/revocation writes an append-only audit record. | Accountability ("glass house") doctrine. | DB (audit table, trigger or explicit write) | Perform each action type; assert exactly one new, correctly-attributed audit row per action. |
| INV-19 | Dean-role sessions never have access to any Studio capability (`CAN_DRAFT`/`CAN_REVIEW`/`CAN_FREEZE_RELEASE`/`CAN_PUBLISH`/`CAN_FLASH_QUIZ`) via any surface, UI or API. | Dean is read-only by design, not by UI convention. | DB (capability grants) + server (endpoint checks) | Attempt every Studio-capability endpoint authenticated as Dean; assert refusal on every one. |
| INV-20 | Educator/staff preview traffic (dev tools, quick-pass, instant-login) is excluded from learner analytics, psychometric calibration, and briefing aggregates. | Test/preview activity must never pollute real evidence. | Server (flagging on session creation) + DB (aggregate view filters) | Generate a preview-flagged session with responses; assert it does not appear in any cohort aggregate or briefing. |
| INV-21 | Dev-only tooling (quick login, instant-pass, seed endpoints) returns 404 outside `NODE_ENV=development`. | Prevents a shortcut meant for testing from becoming a production backdoor. | Server (route guards) | Build in a production-like env; request each dev-only route; assert 404. |
| INV-22 | A validated PLP object can never regress lifecycle state except via the one defined `VALIDATED → VALIDATION_FAILED` branch. | Lifecycle integrity — no silent state corruption. | DB (transition trigger) | Attempt every non-adjacent/reverse state transition; assert all are rejected except the one defined branch. |

Any new invariant discovered during the rebuild is added here with the same
five columns before the feature it protects ships — not after.
