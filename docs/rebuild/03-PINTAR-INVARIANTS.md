# 03 — PINTAR Invariants

*Baseline amendment (2026-11-12): INV-03 amended (a governed, two-person-approved
answer-key correction may withdraw a rationale that contradicts the corrected
key; the option keeps a durable reference to that correction). Owner decision
of 12 Nov 2026 (option A1); ADR-0025.*

*Baseline amendment (2026-09-12): INV-05 corrected (release identity inside
the signed payload); INV-20 strengthened (structural eligibility); INV-23
to INV-38 added for learner identity, transfer, pre/post separation, one
engine, continue-permission, resilience, scoring reproducibility,
certificate identity snapshot, AI trust boundaries, evidence provenance,
metric semantics, publish readiness, and the security non-negotiables not
previously expressed as invariants.*

The authoritative rule list. Every one of these must remain true regardless
of which UI, API shape, or database engine implements it. Treat additions
to this list as requiring the same rigor as adding a new invariant test.

| ID | Rule | Why it exists | Where enforced | How tested |
|---|---|---|---|---|
| INV-01 | Answer keys (option correctness, rationale-to-correct mapping) never reach an unauthenticated or learner-scoped client payload. | The entire assessment's validity depends on this; a leak invalidates every certificate issued against the leaked content. | DB (RLS/view grants) + server (response sanitization before serialization) | Black-box REST test: fetch an item as a real learner JWT, assert no `is_correct`/rationale field present. |
| INV-02 | A hint/scaffold field can never name or narrow to the correct option. | Core Learning Safety Doctrine — assistance must never reveal the answer. | DB (CHECK constraint, regex) + server (dynamic hint generation validated against the same rule) | Attempt INSERT/UPDATE of a hint containing the answer text; assert rejection. Fuzz-generate hints and re-run the same check. |
| INV-03 | Every Option's rationale is non-empty, except where a governed, two-person-approved answer-key correction has withdrawn it because it contradicted the corrected key. Such an Option keeps a durable reference to that correction, the withdrawn text is kept on the correction's audit record, and no further revision of its package may be submitted until the rationale is written. | A wrong answer is evidence of thinking; an unexplained distractor teaches nothing — and an explanation that contradicts the corrected key teaches the wrong thing. | DB: CHECK (non-empty, or null with a withdrawing correction's reference); trigger admitting the reference only from the confirming act or a verified copy, and clearing it when a rationale is written | Attempt INSERT of an Option with no rationale and no reference, an empty rationale, or both a rationale and a reference; assert rejection. Set the reference by any path other than the confirming act or a copy; assert rejection (F13-K16 to K21). |
| INV-04 | Once a PLP Release is FROZEN, its taught-content columns (lessons, items, options, assessment definitions covered by the hash) cannot be modified. | Certificates and audit trails must point at content that provably didn't change after assessment. | DB (immutability trigger) | Attempt UPDATE on a frozen release's item; assert rejection. Recompute hash after an allowed metadata-only update; assert unchanged. |
| INV-05 | A Certificate's signed payload includes the exact `plp_release_id` **and the release's content hash**, the assessment definition identity/version, the identity snapshot (or its hash), the result, the issuance time, the certificate number and the `key_version`. Altering any of these must fail verification. | A certificate must prove which frozen content and which rules it attests to; a binding outside the signature could be swapped without detection. *(Supersedes the earlier "outside the HMAC payload" design.)* | Server (canonical payload builder + signer) + DB (payload fields NOT NULL at issuance) | Issue a certificate; alter the stored `plp_release_id` (or hash, or definition version) in a test copy; assert verification fails. Assert the canonical payload serializer includes every listed field. |
| INV-06 | Certificate verification uses a timing-safe comparison. | Prevents timing side-channel forgery of valid certificates. | Server (verification function) | Static/code-level test asserting the comparison function used; behavioral test asserting near-miss hashes fail identically fast. |
| INV-07 | Certificate signing keys are versioned from the first migration; rotating the active key never invalidates a certificate issued under a prior version. | Security incidents must be recoverable without destroying historical credentials. | DB (`key_version` column) + server (keyring lookup) | Issue under V1, rotate to V2, re-verify the V1 certificate; assert success. |
| INV-08 | `learner_id`/`person_id` on any session, response, or certificate is derived server-side from the authenticated session — never trusted from a request body. | Prevents identity spoofing / attribution forgery. | Server (every write path) | Attempt to submit a response/finalize a session with a forged id in the body; assert the server ignores it and uses its own derived id. |
| INV-09 | Final score and safety-gate pass/fail are computed server-side from raw responses — never trusted from a client-submitted summary — and recomputed independently a second time at certificate issuance. | Two deliberately redundant gates against a single point of forgery. | Server (finalize + issuance paths) | Submit a forged high score in a finalize request; assert the server-computed score is used. Tamper with the stored summary between finalize and issuance; assert issuance recomputes and catches the mismatch. |
| INV-10 | Where safety-critical content applies, a safety-critical item answered wrong fails mastery regardless of overall score (overall passing requirement AND 100% safety-critical requirement). | The Safety Gate must never be defeated by aggregate performance; foundational gaps cannot hide inside a high aggregate. | DB (definition rule) + server (gate evaluation) | Construct a session passing overall score but failing one safety-critical item; assert overall result is FAIL. |
| INV-11 | Hesitation/assistance telemetry never influences scoring, and requesting help never reduces the academic score. | Assistance exists for learning, not for penalizing help-seeking. | DB (physically separate columns/table, no FK from any scoring view) | Query every scoring-relevant view/function; assert none references the assistance telemetry table/columns. Two identical response sets, one with hints used; assert identical scores. |
| INV-12 | An `EXAM`-tier item can never be drawn into a `PRACTICE`- or `TEST`-configured assessment session. | High-stakes item security; prevents item leakage through lower-stakes exposure. | DB (constraint on session-assembly query / bank_type check) | Attempt to assemble a PRACTICE session that includes an EXAM item; assert refusal. |
| INV-13 | Tenant A's data (content, sessions, certificates, briefings, enrollments) is never readable by Tenant B, regardless of role. A learner's portable record crosses institutions only through an executed Transfer (INV-25). | Multi-tenant trust boundary. | DB (RLS keyed off ancestor-path/`institution_id`) | Two seeded institutions; authenticate as a role in Institution A; assert zero rows visible from Institution B on every tenant-scoped table. |
| INV-14 | Every `SECURITY DEFINER` function pins its `search_path` explicitly. | Prevents search-path hijacking privilege escalation. | DB (function definition) | Schema-lint query against `pg_proc`/`pg_settings`; assert no `SECURITY DEFINER` function has an unpinned `search_path`. |
| INV-15 | No storage bucket serving licensed/private content grants `SELECT`/`INSERT`/`UPDATE` to `public` or `anon`; no client ever performs a privileged direct upload. | The C2 root cause, generalized. | DB (storage policies) + server (signed-upload route only) | Anonymous fetch of a known object path; assert refusal. Anonymous/authenticated attempt to overwrite an existing object; assert refusal unless via the server-gated route. |
| INV-16 | A user can never self-grant a role above STUDENT; only an active SYSTEM_ADMIN may grant SYSTEM_ADMIN or platform-level roles. | Anti-privilege-escalation. | DB (grant trigger) | Attempt self-grant as a non-admin; assert rejection. Attempt a non-SYSTEM_ADMIN granting SYSTEM_ADMIN; assert rejection. |
| INV-17 | A role/scope revocation, institutional/scope revocation, security intervention or explicit authorized administrative termination takes effect on the next server-side check, including mid-session — these are the only events that may interrupt an authorized in-progress session. | Time-bounded access must actually bound access; stronger events must be able to interrupt continuation. | Server (middleware + session-check on every scored action) | Revoke a grant mid-session; attempt the next scored action under the old session; assert refusal. |
| INV-18 | Every role-grant, enrollment/membership change, transfer, item edit, release freeze, publication, learning-assignment release move, certificate issuance/revocation, integrity review decision, evidence-eligibility override and administrative session termination writes an append-only audit record. | Accountability ("glass house") doctrine; high-impact actions auditable. | DB (append-only audit table, trigger or explicit write; no UPDATE/DELETE grants) | Perform each action type; assert exactly one new, correctly-attributed audit row per action. Attempt UPDATE/DELETE on the audit table; assert rejection. |
| INV-19 | Dean-role sessions never have access to any Studio capability (`CAN_DRAFT`/`CAN_REVIEW`/`CAN_FREEZE_RELEASE`/`CAN_PUBLISH`/`CAN_QUICK_ASSESSMENT`) via any surface, UI or API. | Dean is read-only by design, not by UI convention. | DB (capability grants) + server (endpoint checks) | Attempt every Studio-capability endpoint authenticated as Dean; assert refusal on every one. |
| INV-20 | Only evidence of class `OFFICIAL` can reach institutional analytics, Question Health, empirical psychometrics, certificates, official learner mastery or production reporting. `PREVIEW`, `SYNTHETIC` and `PUBLIC_DEMO` evidence is excluded **structurally** — consumers read only eligibility-filtered base views/functions and hold no direct grant on raw evidence tables. | Test/preview/demo/synthetic activity must never pollute real evidence, and exclusion must not depend on a developer remembering a `WHERE` clause. | DB (`evidence_class` NOT NULL at write; eligible-evidence views; grants) + CI lint (no analytics/psychometric/reporting code path reads raw evidence tables) | Generate PREVIEW, SYNTHETIC and PUBLIC_DEMO sessions with responses; assert none appears in any aggregate, briefing, Question Health signal, metric or certificate eligibility. Assert analytics roles have no SELECT on raw evidence tables. |
| INV-21 | Dev-only tooling (quick login, instant-pass, seed endpoints) returns 404 outside `NODE_ENV=development`; seed scripts refuse to run without a positive non-production signal. | Prevents a shortcut meant for testing from becoming a production backdoor. | Server (route guards) + seed script guard | Build in a production-like env; request each dev-only route; assert 404. Run the seed without the non-production flag; assert refusal. |
| INV-22 | A validated PLP object can never regress lifecycle state except via the one defined `VALIDATED → VALIDATION_FAILED` branch. | Lifecycle integrity — no silent state corruption. | DB (transition trigger) | Attempt every non-adjacent/reverse state transition; assert all are rejected except the one defined branch. |
| INV-23 | A Person's identity is one platform-wide record; Enrollments and Memberships are dated, append-only records. No enrollment, class or cohort field on a learner is ever overwritten by a period change; historical membership is reconstructable for any date. | Learner identity transcends institutions; history must never be lost to an academic-year rollover. | DB (append-only memberships with `valid_from`/`valid_to`; no mutable `class_id` on Person) | Roll a cohort to the next Academic Period; assert prior memberships remain with a closed `valid_to` and the "who was in class 5A on date D" query still answers correctly. |
| INV-24 | Pre-Test and Post-Test sessions in the standard Dr. Gladys learning cycle share **zero identical items and zero `parallel_group` siblings**. Controlled overlap exists only as a distinct, explicit assessment mode (LATER), never as a relaxation of this rule. | Post-test mastery must not be memorisation of the pre-test. | Server (assembler excludes every item id and every sibling of every item the learner's pre-test presented) + DB (definition mode check) | Assemble a pre/post pair for one learner across the full bank; assert empty intersection of item ids and of parallel groups. Attempt to configure overlap on a LEARNING_CYCLE definition; assert rejection. |
| INV-25 | A learner's records cross an institutional boundary only through an explicit, authorized, audited Transfer, and only the record classes marked portable. Historical evidence keeps its original enrollment binding; nothing is re-parented. | Preserve provenance and institutional privacy while letting the learner's own record follow them. | DB (transfer table + trigger; evidence rows carry immutable `enrollment_id`) + server (transfer workflow) | Execute a transfer School B → School C; assert School C reads the portable record, cannot read School B's institution-scoped records, and School B evidence still carries the School B enrollment id. |
| INV-26 | One authoritative assessment engine: every mode (learning cycle, practice, test, exam, Quick Assessment, public demo, paper foundation) and every item type is assembled, sanitized, scored and evidenced by the same domain services. No second implementation of assembly, sanitization, scoring or the safety gate exists. | The PINTAR 3.0 parallel-engine failure must not recur. | Code structure (single engine module) + CI check | Code-search CI check flags any second implementation of score/safety-gate/sanitizer; contract test that every mode's route calls the engine. |
| INV-27 | Start eligibility and continue permission are distinct: closing an assignment window prohibits new sessions but does not interrupt a session that legitimately started; that session continues to its authorized deadline unless an INV-17 event occurs. | Learners must not lose legitimate work because a window closed while they were working. | Server (session-continue check reads session deadline + INV-17 events, not the assignment window) + DB (session carries its own authoritative deadline) | Open window, start session at T-5min, close window at T; assert responses still accepted until the session deadline and new session creation refused. |
| INV-28 | No legitimate completed work is lost: response submission is idempotent per (session, presented item, client sequence); reconnect/replay never duplicates or silently drops a response; final submission occurs exactly once semantically. | "No lost legitimate completed work." | Server (idempotency keys, unique constraint) + client (durable outbox, replay) | Acceptance scenario doc 07: 17 answered online, 8 offline, process killed, return; assert exactly 25 responses, no duplicates, one finalization. |
| INV-29 | Every Result (and Session) records `plp_release_id`, assessment definition version, engine version and scoring policy/configuration version. Anything whose change could materially alter interpretation of historical evidence is versioned; meaningless implementation details are not. | Historical scoring reproducibility; explaining the rules under which a result was produced. | DB (NOT NULL provenance columns on session/result) + server | Finalize a session; assert all four identifiers present. Change the scoring policy; assert old results still resolve to the old policy version. |
| INV-30 | An issued Certificate's identity presentation comes from its Certificate Identity Snapshot; later changes to the Person's profile (photo, display name, other mutable data) never change an issued certificate or its verification. | Current profile state and historical credential identity are separate concerns. | DB (snapshot stored/hashed at issuance; certificate render reads snapshot only) | Issue a certificate, change the profile photo and display name, re-render and re-verify; assert identical output and successful verification. |
| INV-31 | Any AI capability producing learner-facing output operates in the Learner Assistance Intelligence Context, which structurally has no access to answer keys, correctness, misconception-to-answer mappings, grading secrets or other privileged assessment data. A prompt instruction is never the control. | Security through data boundaries, not AI obedience. | Server (context builder reads only the learner-sanitized item shape; separate credentials/grants for authoring vs learner contexts) | Contract test: diff the learner-assistance context payload against the sanitized learner item type; any privileged field fails. Attempt to build a learner context from the authoring representation; assert refusal. |
| INV-32 | No AI provider is part of the canonical domain model; provider identity appears only as provenance metadata on AI-produced artefacts. No AI or external tool can publish content or assign it to learners; human review and `CAN_PUBLISH` remain mandatory. | Vendor neutrality; AI proposes, PINTAR validates, humans govern. | Schema (no provider-typed entities) + server (publish path requires human capability) | Schema-lint: no table/enum names a provider. Attempt publication via the ingestion/AI path; assert refusal. |
| INV-33 | Every assessment/learning evidence record carries its Evidence Provenance (doc 02) at write time, including evidence channel and evidence class; these fields are NOT NULL and immutable. | Provenance cannot be reconstructed later; eligibility must be decidable from the row itself. | DB (NOT NULL + immutability trigger on provenance columns) | Attempt to insert evidence without channel/class/enrollment/release/definition; assert rejection. Attempt to update the class of an existing row; assert rejection (override is a new audited record, not an edit). |
| INV-34 | Institution report templates may select, order, visualize, title and brand catalogue metrics; they can never redefine a metric's meaning or calculation, and no arbitrary SQL/formula is accepted. | PINTAR owns metric semantics; "the evidence stays the same, only the telling changes." | Server (template schema is a selection over the catalogue) + DB (templates reference metric ids only) | Attempt to save a template containing a formula or an unknown metric; assert rejection. |
| INV-35 | Publish Readiness reports `READY` only when technical validation passed, academic approval is recorded, and no unresolved ERROR-level MCQ Quality Finding exists; it always names exactly what prevents publication. | Calm surface (Ready / Action Required / Blocked) over a governed process. | Server (readiness projection) + DB (publish transition checks the same conditions) | Seed adversarial fixtures (doc 16 §4); assert BLOCKED with the correct finding named; resolve; assert READY; attempt publish while BLOCKED; assert refusal. |
| INV-36 | RLS is enabled and closed by default on every table from creation; no `USING (true)` policy exists on protected production data; storage buckets are private by default. | Convention is not a boundary (Lesson 2); the two-lock storage lesson (Lesson 1). | DB (`ALTER DEFAULT PRIVILEGES`, schema-lint) | Schema-lint CI: every table has RLS enabled; no policy with `USING (true)` on protected tables; no bucket public unless on an explicit allow-list. |
| INV-37 | Service-role credentials never exist client-side; every authenticated route — including in-progress assessment routes — is protected by server-side authorization; security is enforced at the server/data boundary, never by UI convention alone. | Security non-negotiables 10, 11, 14. | Server (middleware on every authenticated route) + build (client bundle scanned for service-role secret) | Bundle scan asserts no service-role key; route inventory test asserts every authenticated route is middleware-covered; direct API call as an unauthorized role is refused independent of UI. |
| INV-38 | Exactly one canonical public certificate verification route exists; no second route shape is ever introduced. | Printed QR codes and public trust depend on one stable route. | Route inventory + CI check | Route inventory test asserts exactly one verification route pattern. |

Any new invariant discovered during the rebuild is added here with the same
five columns before the feature it protects ships — not after.
