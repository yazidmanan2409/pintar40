# 12 — PINTAR Failure Modes (Pre-mortem)

*Baseline amendment (2026-09-12): rows added for evidence contamination,
hardwired pedagogy constants, provider concepts in the domain model,
privileged data in learner-assistance AI contexts, unsigned certificate
bindings, mutable credential identity, silent release reassignment,
membership overwrite on rollover, a second Quick Assessment engine, metric
redefinition by templates, the patch loop, and complexity leaking to the
surface.*

Assume it's twelve months from now and PINTAR 4.0 has again become
difficult to maintain. Here's how that plausibly happened, and how to
catch it early.

| Failure | Early warning signal | Preventive architecture rule | Automated test/metric |
|---|---|---|---|
| **Schema drift** — a second migration series or a long-lived "temporary" branch reappears | Two folders/branches both claiming to be canonical migrations | One trunk, one linear history, from commit one (doc 01 Lesson 4/12; doc 16 §2) | CI check: exactly one migrations directory exists; fail the build if a second is added |
| **Feature coupling** — Studio, Learning, Certification code start importing each other's internals directly | A change to the assessment engine requires touching Studio UI files with no shared contract | Module boundaries follow the five-system split (Studio/Learning/Intelligence/Certification/Care); cross-module calls go through named contracts (docs 06–08), not shared mutable internals | Static import-graph check: no module imports another's non-exported internals |
| **Authorization drift** — RLS policy and application-layer check diverge over time | A permission works differently in the UI than a direct API call | One shared authorization primitive called from both layers (FABLE-01 §4) | The doc-05 matrix, fully scripted as tests, re-run every CI build — any drift fails immediately |
| **RLS gaps on new tables** — a table added in month 8 ships without RLS enabled | A new feature's table shows up in a security review with `USING(true)` or no policy at all | `ALTER DEFAULT PRIVILEGES` set from day one; schema-lint test asserting every table has RLS enabled (INV-36) | Schema-lint CI job run on every migration, not just at launch |
| **Tenant leakage** — a new aggregate view forgets the `institution_id` filter | A dean or educator briefing occasionally shows a number that doesn't match their own institution's data | Every new aggregate view is required to pass the two-seeded-institution isolation test (INV-13) before merge | Add the new view to the standing INV-13 test matrix as part of its own PR |
| **Evidence contamination** — preview, synthetic or public-demo sessions leak into analytics, Question Health, psychometrics or certificate eligibility because a new query forgot a filter | A Question Health signal fires on an item only the persona harness has answered; a demo user "earns" a certificate | Structural eligibility: `evidence_class` NOT NULL, consumers read only eligibility views, analytics roles have no grant on raw tables (INV-20, INV-33) | CI lint: no analytics/psychometric/reporting/certification path references a raw evidence table; persona-harness run asserts zero synthetic rows in any official aggregate |
| **Assessment answer leakage** — a new item field is added and the sanitizer isn't updated | A new field appears in a learner-facing network response that shouldn't be there | Allow-list sanitization for the learner-facing item shape (doc 07) — new authoring fields default to excluded | Contract test: diff the authoring type against the sanitized type; new fields must be explicitly allow-listed or the test fails |
| **Privileged data in a learner-assistance AI context** — someone builds an assistance prompt from the authoring item "so the hint is better" | An assistance request payload contains `is_correct` or `misconception_code`; a prompt says "do not reveal" | Learner Assistance Intelligence Context is built only from the sanitized type (INV-31); prompt instructions are never the control | Contract test diffing the assistance-context payload against the sanitized type; refusal test on building a learner context from the authoring representation |
| **Mutable historical evidence** — someone "just fixes" a bug by editing a FINALIZED session or FROZEN content row directly in the database | A support ticket gets resolved by a manual SQL UPDATE against production | No manual production writes to immutable tables, ever — corrections always go through a new release / new scoring policy version / documented recomputation (doc 08, doc 16 §2) | DB trigger rejecting the write (INV-04, INV-33); a manual `UPDATE` attempt fails, full stop, no admin override path exists |
| **Unsigned or partially signed credential** — a field the certificate attests to (release, definition version, identity) sits outside the signed payload | A certificate verifies after its release binding was changed in a test | Canonical payload includes every attested field (INV-05); payload serializer has a contract test | Tamper each protected field in a test copy; assert verification fails for every one |
| **Credential identity drifts with the profile** — the certificate re-renders from the live profile | A learner changes their photo and an old certificate shows the new one | Certificate Identity Snapshot (INV-30) | Change profile after issuance; assert identical render and verification |
| **Silent release reassignment** — a corrected release is published and learners are re-pointed automatically, or in-progress sessions switch content | Learners report a lesson changed mid-course; results become inconsistent with the content a learner saw | Release-correction / active-learner policy; moves are explicit, audited, not-started-only by default (doc 08) | Publish v1.1 over an assignment with completed/active/not-started learners; assert each class of learner is in the correct state and one audit row per move |
| **Membership overwrite on rollover** — the year changes and `class_id` is updated in place | "Who was in 5A last year" cannot be answered; historical evidence points at the wrong class | Dated, append-only Memberships (INV-23) | Rollover test asserts prior memberships remain with closed `valid_to` |
| **Telemetry inconsistency** — hesitation/assistance data quietly starts influencing a scoring calculation via a "just this once" join | A scoring bug traces back to a query that accidentally joined the assistance table | Physical separation, INV-11, enforced by review checklist on any change touching scoring views | Test asserting no scoring view references the telemetry table (run every CI build, not just once) |
| **Hardwired pedagogy constants** — the hesitation window, late-sync grace, or minimum-evidence thresholds are literals in code | A school asks for a different hesitation window and it needs a deploy | Governed configuration within platform bounds (doc 07); thresholds per signal type (doc 04 §9) | Config-inventory test: every governed parameter resolves from the definition/config, not a code constant |
| **Premature analytics architecture** — building a full statistical (Rasch) engine against zero or fake cohort data | Recalibration code exists and "runs" but every number is derived from seed/demo data, mistaken for real signal later | Doc 09 keeps operational Rasch/IRT LATER; empirical fields honestly empty; predicted ≠ empirical (doc 02) | A flag/metric distinguishing "recalibration ran against OFFICIAL vs other evidence"; alert if non-official-derived numbers are ever surfaced to a real educator |
| **Oversized components/duplicated domain logic** — the assessment-assembly logic gets reimplemented slightly differently in a second route (e.g. a Quick Assessment or Mini-PINTAR engine) | Two different code paths compute "did this session pass" with subtly different rules | One assessment-engine module (doc 07, INV-26) is the only place assembly/scoring/safety-gate logic lives; every mode calls into it | Code-search CI check flagging a second implementation of assembly/score/safety-gate/sanitizer |
| **Metric redefinition by template** — an institution template "adjusts" how a metric is calculated | Two schools' reports disagree on what "mastery rate" means | Canonical Metric Catalogue; templates select and present only (INV-34) | Template-schema test rejects formulas/unknown metrics |
| **Provider concepts in the domain model** — a `notebooklm_source_id` or `claude_run_id` column appears on a canonical entity | Replacing the provider requires a schema migration | AI Provider Gateway; provider identity only as provenance on AI-produced artefacts (INV-32) | Schema-lint: no canonical table/enum names a provider |
| **Client/server business-rule duplication** — a validation rule (e.g. hint-leak check) is implemented once in the DB and reinvented differently in the UI | The UI accepts a hint the database then silently rejects, or vice versa | The DB CHECK constraint is the single source of truth; the UI calls the same validator function server-side before ever showing a save-succeeded state | Test: an input that the DB rejects must also be rejected by the UI-facing validation endpoint, with matching error content |
| **Inconsistent state machines** — a new status value gets added to one lifecycle without updating its transition table | A row ends up in an undefined state no code branch handles | Every lifecycle (doc 04) is enforced by an explicit transition table/trigger, not an open string column | Test: every possible transition is enumerated; any status value with no defined incoming/outgoing transitions fails a schema-lint check |
| **Migration debt** — provisional/"maybe applied" migrations accumulate again | A new migration's comment says "verify this hasn't already run" | Every migration is verified against a fresh clone and the supported upgrade path before merge, in CI (doc 16 §2) | CI runs the full migration set against a clean database and against the previous release's database on every PR |
| **Poor test isolation** — the selftest suite starts depending on state left over from a previous test run | Tests pass locally but fail in CI in a different order, or vice versa | Each test seeds and tears down its own synthetic tenant/data; no shared global fixture mutated across tests (doc 16 §3) | CI runs the suite with randomized test order; flakiness on reorder is treated as a real bug |
| **Weak acceptance gates** — a phase gets marked "done" because most checklist items pass, not all | A known-failing test gets silently skipped or commented out | The verification contract (doc 16 §4): `npm run selftest` is a defined, versioned contract that must exit 0, no partial credit | CI blocks merge on any skipped/pending test without an explicit, reviewed justification comment |
| **Patch loop** — the same gate fails 2–3 times and each cycle adds a patch | Commit history shows "fix", "fix again", "really fix" at one gate | Stop-patch-loop rule (doc 16 §7): stop, find root cause and invalid assumption, clean reproduction, design correction, regression test | Gate-failure counter per gate; a third failure blocks further patch commits until an ADR records the root cause |
| **AI-generated code accumulation** — successive AI sessions each add a slightly different helper for the same thing | Duplicate utility functions doing near-identical things show up in a code review | ADR log (doc 13) records every non-trivial decision so a later session finds the existing one instead of reinventing it | Periodic duplicate-detection pass cross-referenced against the ADR log |
| **Undocumented architectural decisions** — a load-bearing design choice is made once and never written down | A later contributor "improves" a deliberate design because they didn't know it was deliberate | Every non-trivial decision goes into the ADR log at the time it's made (doc 13) | Review checklist: does this PR change something with an existing ADR? If yes, does it update or explicitly supersede that ADR? |
| **Scope creep** — a "quick" feature from LATER/PARK (doc 09) gets built because it seemed easy | A LATER/PARK-listed feature shows up in a phase's shipped code with no product-owner sign-off recorded | Doc 09's categories are binding; moving an item requires an explicit, recorded product-owner decision | PR review checklist item: does this change implement anything currently listed LATER/PARK? If yes, block until confirmed |
| **Speculative abstractions** — a generic "plugin system" or "configurable everything" layer gets built for a need that doesn't exist yet | A new abstraction has exactly one real caller | Prefer the concrete contract (docs 06–08) over a generic mechanism until a second real use case exists; extension points are designed against a named LATER capability | Design-review question on any new abstraction: "what is the second real caller?" — if none, don't build it yet |
| **Complexity leaking to the surface** — the rigor underneath becomes user-visible: versions on certificates, "VALIDATION_FAILED" as learner-facing copy, raw provenance in a teacher's screen, alarms and popups | Users need to understand lifecycle states or evidence classes to do their job | Calm on the surface, rigorous underneath (doc 15): user-facing states are Ready / Action Required / Blocked and plain next actions; internal designations ("PINTAR 4.0", state enums) never leak | Copy/route inventory test: no internal enum or version string in learner/educator/admin/public surfaces; manual calm-surface review remains the one deliberate manual gate |
| **Under-engineering security-sensitive areas** — a new feature ships without its own RLS/authorization test because "it's just an internal admin tool" | A newly-added admin route has no negative-path (refusal) test | Doc 05's rule applies to every route without exception — "internal" is not an exemption | CI requires at least one refusal test per new authenticated route before merge |
