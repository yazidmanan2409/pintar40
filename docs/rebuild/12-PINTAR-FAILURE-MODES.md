# 12 — PINTAR Failure Modes (Pre-mortem)

Assume it's twelve months from now and PINTAR 4.0 has again become
difficult to maintain. Here's how that plausibly happened, and how to
catch it early.

| Failure | Early warning signal | Preventive architecture rule | Automated test/metric |
|---|---|---|---|
| **Schema drift** — a second migration series or a long-lived "temporary" branch reappears | Two folders/branches both claiming to be canonical migrations | One trunk, one linear history, from commit one (doc 01 Lesson 4/12) | CI check: exactly one migrations directory exists; fail the build if a second is added |
| **Feature coupling** — Studio, Learning, Certification code start importing each other's internals directly | A change to the assessment engine requires touching Studio UI files with no shared contract | Module boundaries follow the five-system split (Studio/Learning/Intelligence/Certification/Care); cross-module calls go through named contracts (docs 06–08), not shared mutable internals | Static import-graph check: no module imports another's non-exported internals |
| **Authorization drift** — RLS policy and application-layer check diverge over time | A permission works differently in the UI than a direct API call | One shared authorization primitive called from both layers (FABLE-01 §4) | The doc-05 matrix, fully scripted as tests, re-run every CI build — any drift fails immediately |
| **RLS gaps on new tables** — a table added in month 8 ships without RLS enabled | A new feature's table shows up in a security review with `USING(true)` or no policy at all | `ALTER DEFAULT PRIVILEGES` set from day one; schema-lint test asserting every table has RLS enabled | Schema-lint CI job (INV-14/INV-01 tests) run on every migration, not just at launch |
| **Tenant leakage** — a new aggregate view forgets the `institution_id` filter | A dean or educator briefing occasionally shows a number that doesn't match their own institution's data | Every new aggregate view is required to pass the two-seeded-institution isolation test (INV-13) before merge | Add the new view to the standing INV-13 test matrix as part of its own PR |
| **Assessment answer leakage** — a new item field is added and the sanitizer isn't updated | A new field appears in a learner-facing network response that shouldn't be there | Allow-list sanitization for the learner-facing item shape (doc 07) — new authoring fields default to excluded | Contract test: diff the authoring type against the sanitized type; new fields must be explicitly allow-listed or the test fails |
| **Mutable historical evidence** — someone "just fixes" a bug by editing a FINALIZED session or FROZEN content row directly in the database | A support ticket gets resolved by a manual SQL UPDATE against production | No manual production writes to immutable tables, ever — corrections always go through a new release / a documented correction workflow (doc 08) | DB trigger rejecting the write (INV-04); a manual `UPDATE` attempt fails, full stop, no admin override path exists |
| **Telemetry inconsistency** — hesitation/assistance data quietly starts influencing a scoring calculation via a "just this once" join | A scoring bug traces back to a query that accidentally joined the assistance table | Physical separation, INV-11, enforced by review checklist on any change touching scoring views | Test asserting no scoring view references the telemetry table (run every CI build, not just once) |
| **Premature analytics architecture** — building a full statistical (Rasch) engine against zero or fake cohort data | Recalibration code exists and "runs" but every number is derived from seed/demo data, mistaken for real signal later | Doc 09 keeps Rasch recalibration in category B until N≥30 real responses exist; stub it explicitly rather than faking realism | A flag/metric distinguishing "recalibration ran against real vs. seed data"; alert if seed-derived numbers are ever surfaced to a real educator |
| **Oversized components/duplicated domain logic** — the assessment-assembly logic gets reimplemented slightly differently in a second route | Two different code paths compute "did this session pass" with subtly different rules | One assessment-engine module (doc 07) is the only place scoring/safety-gate logic lives; every consumer calls into it | Code-search CI check flagging a second implementation of score/safety-gate computation |
| **Client/server business-rule duplication** — a validation rule (e.g. hint-leak check) is implemented once in the DB and reinvented differently in the UI | The UI accepts a hint the database then silently rejects, or vice versa | The DB CHECK constraint is the single source of truth; the UI calls the same validator function server-side before ever showing a save-succeeded state | Test: an input that the DB rejects must also be rejected by the UI-facing validation endpoint, with matching error content |
| **Inconsistent state machines** — a new status value gets added to one lifecycle without updating its transition table | A row ends up in an undefined state no code branch handles | Every lifecycle (doc 04) is enforced by an explicit transition table/trigger, not an open string column | Test: every possible transition is enumerated; any status value with no defined incoming/outgoing transitions fails a schema-lint check |
| **Migration debt** — provisional/"maybe applied" migrations accumulate again | A new migration's comment says "verify this hasn't already run" | Every migration is verified against a fresh clone before merge, in CI, not assumed idempotent by inspection | CI runs the full migration set against a clean database on every PR |
| **Poor test isolation** — the selftest suite starts depending on state left over from a previous test run | Tests pass locally but fail in CI in a different order, or vice versa | Each test seeds and tears down its own tenant/data; no shared global fixture mutated across tests | CI runs the suite with randomized test order; flakiness on reorder is treated as a real bug, not a "just rerun it" |
| **Weak acceptance gates** — a phase gets marked "done" because most checklist items pass, not all | A known-failing test gets silently skipped or commented out | The self-test doctrine (FABLE-00): `npm run selftest` must exit 0, full stop, no partial credit | CI blocks merge on any skipped/pending test without an explicit, reviewed justification comment |
| **AI-generated code accumulation** — successive AI sessions each add a slightly different helper for the same thing (three date-formatting utilities, two auth-check wrappers) | Duplicate utility functions doing near-identical things show up in a code review | ADR log (doc 13) records every non-trivial decision so a later session finds the existing one instead of reinventing it | Periodic duplicate-detection pass (can be manual, scheduled) cross-referenced against the ADR log |
| **Undocumented architectural decisions** — a load-bearing design choice (e.g. "why is media a JSONB column, not a table") is made once and never written down | A later contributor "improves" a deliberate design because they didn't know it was deliberate | Every non-trivial decision goes into the ADR log at the time it's made (doc 13) | Review checklist: does this PR change something with an existing ADR? If yes, does it update or explicitly supersede that ADR? |
| **Scope creep** — a "quick" feature from category B/C/D (doc 09) gets built because it seemed easy | A B/C/D-listed feature shows up in a phase's shipped code with no product-owner sign-off recorded | Doc 09's categories are binding; moving an item from B/C/D to A requires an explicit, recorded product-owner decision | PR review checklist item: does this change implement anything currently listed in category B/C/D? If yes, block until confirmed |
| **Speculative abstractions** — a generic "plugin system" or "configurable everything" layer gets built for a need that doesn't exist yet | A new abstraction has exactly one real caller | Prefer the concrete contract (docs 06–08) over a generic mechanism until a second real use case exists | Design-review question on any new abstraction: "what is the second real caller?" — if none, don't build it yet |
| **Under-engineering security-sensitive areas** — a new feature ships without its own RLS/authorization test because "it's just an internal admin tool" | A newly-added admin route has no negative-path (refusal) test | Doc 05's rule applies to every route without exception — "internal" is not an exemption | CI requires at least one refusal test per new authenticated route before merge |
