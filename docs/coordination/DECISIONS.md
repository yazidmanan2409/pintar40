| **D-030** | 24 Sep | **The spreadsheet reader is PINTAR's own (BOB-02), with no new dependency, on these conditions:** <br>(a) bounded input, as built: 5 MB per file, 40 MB unpacked in total, 1,000 archive entries, 10,000 rows, 200 columns, and inflation capped at each entry's declared size; <br>(b) **every scan is linear in its input.** The regex scans for `<row>`, `<c>`, `<si>` and `<t>` are quadratic on unclosed tags (measured at the gate review: 391 KB of unclosed `<row>` takes 4.6 s, and the 40 MB budget would take hours), so an uploaded file can hold a server function until it is killed. | **D-031** | 24 Sep | **Year-1 capacity target is an acceptance requirement.** The signed MOU expects at least **150 schools × 400 students = 60,000 students** in the first year, plus their staff. *(Yazid)* <br>**Load levels** (simulated active students, one synchronized window): **L1** 400 (one school) · **L2** 4,000 (10 schools) · **L3** 10,000 (25) · **L4** 20,000 (50) · **L5** 60,000 (150, to find where PINTAR degrades; passing is not required). <br>**The scenario is the whole journey**, not a page count: the morning class-card sign-in wave; then start an assessment, answer, change answers, sync, drop and regain the network, submit, results, and teachers opening their class reports. <br>**Pass criteria** (initial, revisable only with evidence): no answer lost or duplicated; server errors under 0.1% (deliberate refusals excluded); answer save p95 under 1 s and p99 under 3 s; no connection-pool exhaustion; the database back at its baseline within 10 minutes of the spike. Each run records latency, error rate, database CPU, memory, I/O, connections, locks and the slowest statements. <br>**Onboarding follows capacity:** L1 passes before the sprint 1 release; at most 10 active schools until L2 passes, 25 until L3, 50 until L4; L5 is run and its breaking point recorded before a school beyond the 50th. <br>**Rules:** load is never run against production (D-013); it runs on a staging Supabase project on the same compute tier as production. A failing level is fixed in the query, index or data-access path first, and hardware is raised second. | The number that matters is concurrent activity, not accounts. An assessment deliberately writes answer state, sync, integrity observations and audit rows, so it costs far more than a page view. At the 24 Sep review a concrete risk was found: class-card sign-in and session refresh reach Supabase Auth from PINTAR's server, so every student shares the server address's per-address limit (bursts of 30, per Supabase's rate-limit docs). A single class signing in together may exceed it, and the card screen reports that refusal as a wrong card or PIN. |

Today nothing can be published, so nothing is exposed. |
