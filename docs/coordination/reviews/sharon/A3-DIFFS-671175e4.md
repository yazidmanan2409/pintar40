## Addendum, 17 Nov 23:40 UTC: the harness's signed-in learner. Second Eye's proposal is accepted.

**The question:**
- `selftest.as_user` (`selftest/db/fable01.sql:20`) sets claims `{sub, role, email}`, with no `session_id`.
- Under S11 (a null `sesi_saya()` refuses at every controller boundary), every fixture that writes as a learner would then be refused.
- **The rule is right, and the harness is what is wrong:** a real token always carries `session_id`.

**Ruling: accepted, a fixed harness session per person.** That means `session_id = md5('selftest-sesi:' || uid)::uuid`, added in `as_user` and `as_user_uid`. One person is then one device across repeated calls. **Conditions:**
1. **Harness only.**
   - `as_user` lives in `selftest/` and in no file under `supabase/migrations/` (I checked, and none at `b5cd166a`). It must stay unreachable on staging and production.
   - **Add a static check** that no migration defines or calls `selftest.as_user`, and none derives a session from `md5('selftest-sesi:'…)`.
2. **No product trust.** Product code reads the session only through `sesi_saya()`, from the claims (D2), and **the controller check stays ownership first** (my 23:00 §5 clarification). So a harness session id gives no rights beyond the person's own sittings.
3. **The explicit cases stay explicit:**
   - S11: claims with no `session_id`, refused;
   - two sessions of one person, A3-R01 style: the second session is refused SITTING_NOT_CONTROLLER on a sitting the first controls;
   - **two persons never share a session:** a self-test asserts that the derived ids differ, for two personas.
4. **Its own test-only commit, before the controller,** with a message that names the change and the reason, and a full suite on it: **green before the controller lands, red nowhere.** It proves that the change alters no current test's outcome.
