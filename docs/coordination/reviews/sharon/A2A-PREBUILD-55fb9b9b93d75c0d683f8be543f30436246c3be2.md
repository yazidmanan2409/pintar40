## Required changes (the page carries them)

**1 · Every reader of a window's schools becomes node-aware.**
- A class-scoped window still has its school in `institution_ids`, because the table's existing CHECK requires
  `platform or cardinality(institution_ids) > 0`. Every reader that matches on `institution_ids` alone would treat it
  as **school-wide**. There are 28 such references today (`20261120100000…`, 24; `20261221100000…`, 4).
- **Required:**
  - the page lists each reader: the hook (`maintenance_block_for_me`, `maintenance_affects`), `pintar_status_saya`,
    `maintenance_draining`, the sitting-start trigger, `maintenance_collisions`, `maintenance_may_act`, the lists and
    notices, and the pause page;
  - it states for each how a non-empty `node_ids` narrows it to the class.
- **Test:** a class-scoped EMERGENCY window affects the class's learners and teachers, and nobody else in the school,
  through **every** reader on that list, not only the hook.

**2 · The node column is validated, beyond the CHECK.**
- A CHECK cannot look at other rows. A trigger on insert and update requires that:
  - each id in `node_ids` is a class node;
  - it belongs to the window's one school;
  - `cardinality(institution_ids) = 1` when `node_ids` is non-empty;
  - the window is not platform-wide.
- `stop_pintar_now` refuses a bad node with a designed code before the trigger does.

**3 · The lock order, stated in full.**
- The page says "the emergency fence first". That holds for the stop and the lift, but **not** for a suspension.
  `tangguhkan_akun` takes the person row, then the account rows (`akun_kunci`), then holds the person's sittings
  (`pengerjaan_tahan_orang`). D6.5 makes that hold a fenced decision, so its fence comes **after** the person and
  account locks.
- That is safe only if no transaction holding the fence ever asks for a person or account row afterwards.
- **Required:**
  - state the order as **person → accounts → fence → sittings in id order**;
  - state the rule above;
  - test it. The structural test checks that no fenced function locks `persons` or `accounts` after its fence call.
    The suspend-during-stop scenario (B6) runs on two real connections with the stop's activation in progress.
- This is my standing person-before-account rule, extended to the fence.

**4 · How the writer enumeration finds the writers.**
- **From the catalogue,** not a list kept by hand: every function and trigger function whose definition writes the
  named tables or columns.
- **Triggers count as writers.**
- **Dynamic SQL:** any function that builds SQL with `execute` and touches those tables must be on the declared list,
  with its reason.
- **No direct grants:** the test also asserts that no client role holds INSERT, UPDATE or DELETE on
  `assessment_sessions`, `learning_assignments`, `lesson_progress` or `maintenance_windows`.
- **Plants:** an unclassified writer turns it red, and so does a fenced writer with its fence removed.

## The four questions

- **And then what?** A class-scoped emergency stops exactly that class's people. After the lift every sitting has
  the time it had.
- **What else did that change?** Every reader of a window's schools (required change 1). The suspension path's lock
  order (required change 3). The closer becomes a procedure.
- **What happens when things go wrong?** There is no half-stop. A failed lift leaves the stop in force. An
  unclassified writer fails the enumeration.
- **Can it be reversed, and what survives?** The lift reverses the stop. The audit keeps `T_stop`, marking and
  `T_lift`. A suspension hold survives the lift.
