## L1F4-A1 · a deletion racing a reopen (Bob's question): defect; gates L1-F4

**Confirmed in the code.**
- `hapus_data_pribadi` checks that an open closure exists (`ACCOUNT_NOT_CLOSED`) **before** it takes
  `persons … for update`.
- `buka_kembali_akun` locks the REOPEN request and the suspension row, never the person.

So the two never conflict on one row. Suppose the deletion's check passes, then the reopen ends the closure, revokes
the roles, unlocks the accounts and commits. The deletion then anonymises the person. The new role check reads the
*open* closure row, so it is empty in that order too, as Bob says.

**Why it gates L1-F4.** It predates L1-F4, but it is irreversible, it destroys a person the platform has just
restored, and it is exactly the "deletion while something live exists" case that §3a.3 asks the deletion to refuse.

## L1F4-A2 · a reopen of an anonymised person (new; gates L1-F4)

The deletion leaves the closure row open. That row is what keeps every account locked. Neither `minta_buka_kembali`
nor `buka_kembali_akun` reads `anonymized_at`, so:
- a REOPEN request made **before** the deletion and still open; or
- one made **after** it, by PINTAR ID (still on the record) or by username (the deletion sets a pseudonymous
  username, so only the PINTAR ID route reaches it);

can be approved. The approval ends the closure and calls `akun_kunci(false)`.
- **A learner's class card is not retired** by the deletion, so it signs in again.
- **An email account** gets back the PIN recovery that L-1 blocks only while the person is locked.

Either way the anonymised record is reconnected to a live sign-in, against the owner's ruling (digest, ruling 21) that
a returning individual is a new person and their history does not reappear.

## The fix (both items)

1. **`hapus_data_pribadi`: lock first, then check.** Take `persons … for update` before the closure check, and read
   the closure and both attachment checks under that lock.
2. **`buka_kembali_akun`, and `aktifkan_kembali_akun` for the same order: person first.** Take `persons … for update`
   before the suspension row and before `akun_kunci`. In `buka_kembali_akun`, refuse when `anonymized_at` is set,
   with a designed code the platform admin sees (for example `ACCOUNT_ANONYMISED`; the wording is Daisy's). With
   step 1, the two acts serialise:
   - reopen first: the deletion is then refused `ACCOUNT_NOT_CLOSED`;
   - deletion first: the reopen is then refused as anonymised.
3. **`minta_buka_kembali`: record nothing for an anonymised person.** Its answer is already the same for everyone
   (`ok`), so nothing is disclosed.
4. **Recommended, not required:** the deletion ends any open REOPEN request for the person, with a note, so none is
   left waiting that can only be refused.

## The four questions

- **And then what?** A deleted person stays deleted. A reopen can no longer restore them, either sequentially or by
  racing the deletion.
- **What else did that change?** The reopen and reinstatement paths gain the person lock, and the reopen gains one
  refusal. No screen changes, apart from the refusal line for the platform admin.
- **What happens when things go wrong?** Today, two admins acting at once, or one approving an old request, can
  irreversibly anonymise a reopened person, or reconnect an anonymised one. After the fix, one of them is refused.
- **Can it be reversed, and what survives?** Anonymisation cannot be reversed. That is why both gate L1-F4. The
  closure row, and the lock it keeps, survives the deletion for good.
