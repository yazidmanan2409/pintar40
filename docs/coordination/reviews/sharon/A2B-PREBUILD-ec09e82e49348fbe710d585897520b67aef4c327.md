## Required points

**1 · The guard's clock is the statement's, not the transaction's** (anticipable: Q4, the same shape as L1-F4's
timestamps).
- "Active" and "approaching" must be read against `clock_timestamp()`, or at least `statement_timestamp()`, never
  `now()`.
- `now()` is the transaction's start. A long transaction that began before `starts_at` would keep reading the window as
  not yet active and could write the class's work inside it. Examples: an import, `kenaikan_tetapkan`, a batch assign.
- State it in row 1, and test it: a transaction begun before `starts_at` whose write comes after it is refused.

**2 · Extend and the window's state** (anticipable: Q4).
- **State is decided by `starts_at`, `ends_at` and `ended_at`, read against the clock. Never by
  `activation_recorded_at`.** That column is the edge recorder's bookkeeping, and it can be one run late because of
  `skip locked`.
  - The page lists `activation_recorded_at` among what tells a window's state (question 4). Remove it from that list,
    or say it is audit only.
- **Extend is refused once `ends_at <= clock_timestamp()`,** whether or not the recorder has marked the end. An elapsed
  window is not extended back to life.
- Test the two orders on two real connections (the shared harness):
  - recorder first: its mark, then the extend refused;
  - extend first: the recorder skips, its next run reads the new `ends_at` and records nothing;
  - either way, exactly one activation and at most one deactivation audit row per window.

**3 · How A2b lifts A2a's rule that a class-scoped window must be an emergency** (anticipable: Q2, the neighbouring
act).
- A2a adds the CHECK `cardinality(node_ids) = 0 or kind = 'EMERGENCY'` and a node-validation trigger (my A2a required
  change 2). The page does not say what A2b does with them. It must state:
  - the CHECK is dropped in the same migration that adds the node parameter to `schedule_maintenance`;
  - `schedule_maintenance` gains a **designed refusal** for a bad node **before** any constraint can fire (as I ruled
    for A2a);
  - the validation trigger now covers PLANNED class windows too: class nodes of the window's one school, not
    platform-wide;
  - a test that a PLANNED class window is accepted after A2b and refused with the designed code for a bad node.
