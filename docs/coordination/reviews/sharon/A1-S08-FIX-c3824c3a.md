## The owner's questions
**(a) Root cause, not symptom: YES.**
- **The cause:** the test assumed it was the only closer, while CI's database runs the live `*/5` job. main ci 45779343510 showed a real run closing the sittings first.
- **The fix removes that assumption:** the live job is paused for the scenario with `cron.alter_job(…, active := false)` and switched back on after it.
- It follows the harness's existing pattern (`a2a-skala.ts:85/278` pauses jobs the same way).

**(b) Nothing weakened, and the five-minute job is still verified: YES.**
- Every existing assertion is unchanged: K0 «before the job», the planted-failure outcomes, the idempotent third run and the double-install.
- «exactly one active */5 job, its role and database» is still asserted, **after** the job is switched back on. So the test still proves the job is installed and active.
- **Two assertions are added:**
  - `cron.log_run` must be on, otherwise the test fails;
  - **no run of the job started at or after the moment the deadlines moved** (`cron.job_run_details`).

**(c) The 1.5 s bound: principled, and not load-bearing for correctness.**
- **What it does:** the wait is "no run starting or running" **and** one launcher loop (1 s) plus margin since the pause.
- **Why correctness doesn't depend on it:** the new assertion makes the test **fail closed**.
  - Any run that starts after the deadlines move turns it red.
  - A run that started before them cannot take these sittings: the wait required that none is under way when they move.
- So the bound only lowers the chance of a red. It can't produce a false green. It is a reasoned condition, not an arbitrary sleep standing in for a guarantee.

**(d) The sweep: A1-S08 is the only test that asserts the intermediate state. I agree with Bob.**
- **A1-S09** (`a1-layar.test.ts` ~425–446) commits past deadlines and races the job's command against itself, the learner and the teacher. **Its assertions are end states**, with the teacher race accepting either outcome. A live run produces the same end states, so it can't turn them red.
- **DR-D02** (`dr150b.test.ts` ~1054) restores one sitting and asserts the end state `S|1|FINALIZED/DEADLINE/1/1`. A live run gives the same end state.
- **Non-blocking (ledger):** in both, a live run landing first would make the test **pass without exercising its race**, which is vacuous for that run. Pausing the job the same way would make them prove what they say. This is for AR-79's harness work, with F04-S04 and CI-W54322.

**(e) A pause that leaks: bounded, with no production exposure.**
- **What re-enables the job:** it is switched back on right after the scenario, before any early `return`, and again in `finally`. The early return after a failed pause also passes through `finally`.
- **The residual:** a **killed** process (SIGKILL, a runner crash, a CI timeout) between the pause and `finally` leaves the job inactive in **that** database.
  - **In CI:** the database is per job and discarded, so there is no carry-over.
  - **On a persistent local stack:** the next A1-S08 run re-enables the job. No other test depends on it being active.
- **Non-blocking hardening (ledger):** have A1-S08 (and `a2a-skala`'s pauses) refuse to pause unless the database is the local stack (127.0.0.1:54322). Then the suite pointed at a shared database could never stop its closer.
