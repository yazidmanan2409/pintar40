## Answers to the three questions

**1 · Lesson progress (row 2a): the guard goes in `record_lesson_progress`, with no new column.**
- It receives the assignment (`p_learning_assignment`), so it can ask the place question exactly.
- What makes it complete is a test, not a column: a static and database check that no client role can insert or
  update `lesson_progress` directly, and that `record_lesson_progress` is the only function that writes it. A later
  writer then fails that check instead of slipping past.
- The refusal is quiet: its own code (answer 3), no redirect, and reading stays open. Whether the reader shows a note
  that progress is not being saved is Daisy's.

**2 · The classing of the five writers: agreed, with three precisions.**

| Writer | Ruling |

| `move_learning_assignment_release` | **Refused.** It is a routine staff change to the class's work. The governed `koreksi_kunci_pindah` stays allowed, for the reason the page gives: it changes only what new starts use, and it is an integrity correction across classes |

## The four questions

- **And then what?** A planned window on 7A stops 7A's writes and leaves its reads open, with a banner. The same
  teacher or learner works normally everywhere else.
- **What else did that change?** The request hook loses class- and school-scoped PLANNED windows. The writers gain
  the place question. The status read and the client tell person-level from work-scoped.
- **What happens when things go wrong?** An unclassified writer fails the enumeration. A refused write has its own
  code and never sends the person to the pause page.
- **Can it be reversed, and what survives?** A window's end lifts every place refusal at once. System closures keep
  running throughout, so no work outlives a window because of it.
