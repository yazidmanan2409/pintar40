## Bob's question: a foreign key to `persons` inside an Auth write

The concern is sound in principle. The suspending act holds the person `FOR UPDATE`, which conflicts with
`FOR KEY SHARE`. An Auth write, holding `auth.users`, that inserts a row with a foreign key to `persons` would wait on
the suspension while the suspension waits on `auth.users`.

**Checked: no such insert is reachable on this tree.**
- **Auth's guards.** `auth_card_email_guard`, `auth_email_correction_guard` and `auth_password_write_guard` (with
  `recovery_restore_core`) insert only into `account_setup` (foreign key to `accounts`, a row the same transaction
  already holds), `recovery_ladder` (keyed by a text id) and `audit_log` through `audit_write`. Everything else they
  do is an update.
- **`audit_log`.** Its `actor_person_id` has **no** foreign key (`20260912004158`, line 77).
  `evaluation_actor_person_id` has one (`20260917120000`). `audit_write` fills it only from an open evaluation session
  whose `persona_auth_user_id = auth.uid()`.
  - Inside Auth's own write there is no request JWT, so `auth.uid()` is null, the column is null, and no key check
    runs.
  - Even if it were filled, the key would name the **evaluator**, not the person being suspended.
- **L1-F4's guards** are INSERT-only, and none of these inserts is into a guarded table.

**To keep it so:** add one line to the path list. "No function reachable from a trigger on `auth.users` inserts a row
with a foreign key to `persons`, except through `audit_write`'s evaluation column, which is null inside Auth's
writes." This is a statement, not a test; a later batch that adds such an insert reopens it.
