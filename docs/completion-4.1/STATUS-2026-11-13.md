## 5. Current batch in detail: A2a change A

**Purpose:** the lock-order safeguard the owner decided after the 4.0 look-back. It is one test that reads every
database function and checks that people, enrolments, suspensions, Auth users, accounts and sittings are always locked
in one agreed order.

**What it found:** ten real defects in existing code, all caught in development and none in acceptance.

| # | Where | What could happen | Fix | Proof |
|---|---|---|---|---|
| 1 | Password recovery | A recovery could wait on a locked person and time out. It was reachable today; it was first thought latent, and a test corrected that. | Recovery no longer reaches a person lock | Race test, timed out on old code |
| 2 | Finishing a sitting, plus 9 sibling functions | Finishing a learner's sitting at the moment they are suspended deadlocks | Learner locked first | Deadlock reproduced, then fixed |
| 3 | Ending an enrolment | Ending an enrolment during the same learner's promotion or transfer deadlocks | Learner locked first | Deadlock reproduced, then fixed |
| 4 | Transfer request, new-account activation | Would become new cycles once #3 was fixed; caught before they existed | Same commit as #3 | Race test |
| 5 | Answer-key correction | Breaks the order A2a relies on; not live today | Learner locked first | Structural check |
| 6 | Result recalculation | Narrow real cycle with the key correction | Learner, then sitting, locked first | Structural check; race on the register |

- **Severity:** in every case the worst outcome was one action cancelled with an error. No data could be lost or
  corrupted.
- **Findings judged not real**, and documented as exceptions backed by checks so they cannot silently become real:
  - the permit functions, since nothing in PINTAR deletes Auth users;
  - account changes passing through the password guard when the password isn't changing;
  - harmless re-locks of a row a function already holds;
  - brand-new rows nobody else can see yet.
- **Register:** eight items, REG-A2A-01 to -08, each named in the test. None touches A2a's area. One example is the
  broader lock change Sharon deferred, because it would weaken how a deletion is ordered against new data.

### How it went

- **Duration:** about four and a quarter hours of development, against a one-day estimate, then one acceptance run.
- **Convergence was the main risk.** Each improvement to the test revealed more existing problems, at one point 76
  reports. The test was frozen and one reading pass with no fixes was required; Sharon added two limits. After that it
  converged.
- **Anticipation:** Sharon judged nine of the ten defects reasonably anticipable, mostly by the question about locks.
  The tenth was not, because foreign-key locks weren't counted until her rule that morning.
- **Roles worked as intended.** Sharon corrected her own reasoning when Second Eye's race test disproved it. Second Eye
  stopped at every change to approved behaviour instead of fixing silently. Daisy caught a false message a learner
  would have seen, before any code existed.
